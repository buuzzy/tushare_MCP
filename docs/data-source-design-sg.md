### 关键行为特征

1. **腾讯（新加坡节点）**：单请求极其稳定（0.5s），串行 2 QPS 无压力、允许 ≤5 并发。**但存在一个致命的协议行为**：当请求区间的 end ≥ 当前日期（周末/未来日期）时，返回的不是空数据而是「区间内最后一根旧K线」（如周五收盘那根）。
2. **东财 push2his**：单请求正常且能一次返回全历史（这是它最大价值），但**对并发零容忍**（5 并发即全部断连）、连发也会间歇失败（7/12）。仅适合作为"低频、严格串行"的备源。
3. **新浪**：本轮最大惊喜——美股全历史 0.28s/次、15 连发+5 并发全过，吞吐三家最强；港股 K 线也有可用端点（klc2_kl.js，akshare 自带 JS 解码）。
4. **A股 tushare（付费）**：海外可达、秒级，维持主力不动。

## 二、发现的 P0 缺陷（本轮摸底的意外收获）

### 分段循环游标倒退 → 无限循环（周末 100% 触发）

`_fetch_tx_kline` 的游标推进用 `cursor = last_date + 1天`。当 end 是周末/今天时：

```
游标 = 2026-09-19（周六）→ 请求 09-19~09-20 → 腾讯返回 1 根旧K线(09-18)
→ last_date+1 = 09-19 = 原游标 → 永不推进 → 无限循环直到 120s 被强杀
```

**这解释了全部历史现象**：
- 「时好时坏」= 交易日正常（last_date==end 终止）、周末必挂（用户恰在周末测试）
- 日志里没有任何慢响应 = 每次请求都是 0.5s 成功的，只是循环不终止
- 显式区间如果恰好以周五结尾就正常（如 20250101-20260918 ✓）

**修复（一行级）**：`cursor = max(last_date, seg_end) + 1天`；同时把 end 归一化到 ≤ 最后交易日。

### 其他待修项

- 工具级超时 120s → **55s**（MCP 客户端 60s 就放弃，服务端必须先出结果）
- 东财备源调用强制串行（max_concurrency=1）

### 3.3 超时链路（目标：用户端 ≤55s 必有响应，P95 <10s）

```
上游单请求:  connect 3s / read 10s
内部重试:    2 次（退避 0.5s/1.5s，现有）
源切换:      主源整体失败(含熔断) → 备源接管，切换本身不计入用户等待
工具级上限:  120s → 55s（超时前必须返回明确错误或部分数据）
缓存命中:    毫秒级直返
```

## 五、边界说明

- 本设计基于**当前时点**的新加坡节点实测；数据源的反爬策略会漂移（腾讯上周还挂、本周就通），所以 em_client 的熔断+源自动切换是长期保险，限速参数只是起点。
- 探针工具（source_probe）已部署保留，以后任何疑似"数据源劣化"都可以 30 秒重跑摸底，不用猜。
- 东财 push2his 虽然本轮在新加坡表现脆弱，但它"单请求全历史"的能力不可替代（腾讯要 4 段拼 3 年），作低频备源最合理。
